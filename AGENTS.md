# CRL Hitbox project constraints

- This is a Minecraft 1.12.2, Cleanroom-only, Java 25 project. The minimum implementation and API baseline is Cleanroom Loader `0.6.8-alpha`; compile and verify against that exact baseline without dynamic versions, dependency substitution, or later-only APIs.
- Preserve the Gradle wrapper, plugin, mapping, repository, manifest, and loader conventions derived from the read-only local template at `D:\WI - Dev Workspace\CleanroomModTemplate`. Do not upgrade them without explicit authorization.
- Use `C:\GradleCaches` as `GRADLE_USER_HOME` unless an explicit project-local configuration supersedes it. Build with the target wrapper.
- Keep the geometry package JDK-only, common/server-safe, and independently compilable with Java 25 and an empty external classpath; retain `compileGeometryIsolation` as a `check` verification dependency. Do not introduce gameplay examples, platform adapters, capabilities, networking, rendering, combat orchestration, certified geometry, debug hooks, coremods, Access Transformers, or Mixin injections without a later scoped task. The roadmap's F3+B debug overlay is such a scoped task (roadmap R4 and §13.8): client-only debug rendering confined to `dev.crlhitbox.internal.client` is authorized, must keep common/server classes free of client class constants, and never changes query semantics; Mixin, Access Transformers and coremods remain unauthorized.
- Keep common/runtime-hitbox code dedicated-server safe. Client-only code must remain isolated and must never link on a dedicated server.
- The functional target is the collision feature set described by HitboxAPI's public README and public interfaces, implemented independently in this project. HitboxAPI (`https://github.com/AnECanSaiTin/HitboxAPI`) is a read-only functional reference: do not copy or adapt its source, algorithms, network protocol, license, package structure, assets or tests, and do not treat it as a correctness oracle. The handover roadmap `docs/CRL_HITBOX_ROADMAP.md` defines the current scope, acceptance matrix, phases and method-level API proposals; it is the authoritative plan for this project's next stage.
- Collision queries are pure queries: they must not execute damage, callbacks, world mutation, networking, rendering, persistence I/O, logging on normal query paths, or depend on time, randomness, or thread-local state. Runtime results are ordinary pointwise IEEE-754 double results, not certified geometry, and must never become authority for certified interval geometry, admission, continuous terrain non-penetration, persistence truth, or proof receipts. Platform code in later phases must convert at the geometry-package boundary instead of leaking platform types into it.
- The project identity is finalized as Maven group and Java base package `dev.crlhitbox`, main class `dev.crlhitbox.CrlHitbox`, and development version `0.1.0-SNAPSHOT`. Preserve this identity unless the user explicitly changes it.
- No license has been selected. Do not add a license, SPDX header, publishing configuration, commit, tag, release, or push without explicit authorization. Preserve the third-party notices already recorded in `THIRD_PARTY_NOTICES.md`.
- Keep `Solid3d` sealed to `Aabb`, `Sphere`, `Obb`, `Capsule`, and `Composite`; `Segment3d` remains a bounded non-solid query primitive. Geometry-level `Composite` values contain only canonical solid leaves and no transforms, IDs, names, metadata, callbacks, or platform behavior. Generic dispatch must route every primitive narrow phase through the existing typed kernels.
- `RigidTransform3d` is the sole pure rigid-transform value owner, with composition fixed as `a.andThen(b) = b ∘ a`. Future AABB projection must not silently lose exact min/max endpoint semantics, and no transformed-solid wrapper or production solid projection may be added without a separately reviewed phase.
- `PlacedSolid3d` is the sole pure local-solid plus rigid-placement owner. It remains `Bounded3d`, never `Solid3d`, and must not expand `Solid3d` permits. Local AABB min/max intervals must remain direct rather than center/half recoded; placed bounds pruning is negative-only. Platform holders must consume these placement semantics instead of duplicating their own projection policy.
- `EntityHitboxHolder` stores deterministic `ResourceLocation` to entity-local `PlacedSolid3d` mappings and must retain no `Entity` or `World` reference. Its parent frame remains caller-defined until a separately reviewed pose adapter phase.
- Only effective holder mutations advance its checked monotonic revision. `EntityHitboxSnapshot` values are immutable deterministic captures, while holders remain logical-game-thread-confined mutable identity state.
- The Entity capability is server-safe, side-local, non-sided for facing access, and non-persistent until a separately versioned persistence phase. No networking, synchronization, combat, or pose extraction may be hidden inside holder mutation.
- Platform code remains outside the byte-for-byte frozen geometry production package and must remain free of client-only linkage.

Resolving the representation prerequisite is an independently verifiable core change, not completion of Phase 2B networking.
